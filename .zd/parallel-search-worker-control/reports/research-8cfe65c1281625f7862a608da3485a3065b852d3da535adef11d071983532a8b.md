# Research report: parallel-search-worker-control

## Question

> Verify issue parallel-search-worker-control-011 against the integrated durable Origin/Variant migration evidence and determine whether every acceptance criterion is satisfied

## Summary

> Yes. The captured integrated repository evidence satisfies all five acceptance criteria of issue parallel-search-worker-control-011. The API fixtures enforce both sides of the breaking contract: current Origin/Variant overrides must compile, while either removed master/slave override must not. Registered executable scenarios exercise Origin-only, Variant-only, and combined callbacks for RBS, single-asset PBS, sequential multi-asset PBS, and threaded parallel PBS. The RBS scenarios distinguish Origin restart decisions and Variant completeness decisions; the PBS callbacks deliberately return false while the tests still require solutions and exact dispatch counts, demonstrating that PBS ignores those return values. The migration example is a build target and gives the exact old-to-new declarations with no aliases. Finally, a repository-walking verifier compares every detected case-insensitive whole-word occurrence, including plurals, against an occurrence-level classified manifest and fails on any count or evidence mismatch. Issue 012 records these durable artifacts as completed. The packet does not contain command transcripts, so it supports acceptance from the integrated validation design and retained artifacts, but it does not independently replay the broader validation commands listed below the acceptance criteria in issue 011.

## Limitations

- The packet contains bound source snapshots and issue metadata, but no stdout, exit status, or verifier report from a fresh build/test run. It proves that acceptance-sensitive fixtures, scenarios, build wiring, and the retained inventory exist; it does not independently replay their execution.
- Threaded-parallel Origin-only and Variant-only scenarios are correctly guarded by `GECODE_HAS_THREADS`. The captured source cannot demonstrate their runtime result in a particular threaded build without an execution transcript.
- Issue 011's Validation section also asks for complete sequential/threaded Search suites, documentation/example builds, terminology scans, and `zd issues check`. Those commands are broader procedural validation than the five acceptance criteria, and their results are not captured in this research packet.

## Recommendations

- Mark all five acceptance criteria in issue 011 satisfied from the integrated durable evidence, while linking the already-recorded issue-012 verification report or command evidence when completing issue 011 so the broader Validation section remains auditable.
- Retain the positive and negative compile fixtures, MetaDispatch scenarios, migration example, terminology verifier, and occurrence manifest in normal CMake and Autoconf workflows; together they prevent the migration contract from silently regressing.
