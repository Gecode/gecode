# Research report: parallel-search-worker-control

## Question

> Research issue parallel-search-worker-control-002: Specify worker-control API and meta-engine ownership

## Summary

> Adopt a copyable public value handle whose identity is shared across copies:
> 
> ```cpp
> namespace Gecode { namespace Search {
>   class GECODE_SEARCH_EXPORT WorkerControl {
>   public:
>     WorkerControl(void) noexcept;                 // empty / no control
>     explicit WorkerControl(unsigned int requested);
>     explicit operator bool(void) const noexcept; // engaged
>     unsigned int requested(void) const noexcept;
>     void request(unsigned int workers);          // asynchronous update
>     unsigned int capacity(void) const noexcept;  // 0 until first bind
>   };
> 
>   class Options {
>   public:
>     // existing fields, including double threads
>     WorkerControl worker_control;
>   };
> }}
> ```
> 
> `Options::threads`, after `expand()`, remains the construction-time maximum. `WorkerControl(n)` creates an unbound shared state with initial request `n`; engine construction publishes the rounded maximum as its immutable capacity. The engine creates all workers and barrier members from that maximum. `request(n)` only publishes a desired execution-slot ceiling and wakes the scheduler; it does not wait for convergence, interrupt propagation or recomputation, create workers, or change barrier membership. Shrink takes effect when workers reach safe exploration boundaries. Growth wakes eligible parked workers. Before convergence, an in-flight worker may still be finishing a boundary under the old request. Zero is never valid.
> 
> The handle is an identity-bearing value, not a configuration scalar. Copies share one ref-counted state. The caller, copied `Options`, builders, RBS, and the concrete engine may all retain copies without retaining pointers to one another. The shared state owns the atomic request and wake-generation/event, so `request()` never dereferences an engine. During destruction the engine keeps its state until parked workers are woken and every worker has joined; afterward requests remain memory-safe and merely update inert state. `capacity()` stays available after destruction.
> 
> One public control identity binds to one logical search engine. A second unrelated engine constructed from a copied `Options` containing the same engaged control throws `Search::WorkerControlInUse`; callers wanting independent engines create independent controls. RBS owns the logical binding and transports an internal attachment token to its current child. Reset or replacement of that child preserves the same state and capacity; a replacement is not a second public binding. This distinction prevents copied options from accidentally turning one handle into an ambiguous broadcast controller.
> 
> Invalid behavior is explicit. `WorkerControl(0)` and `request(0)` throw `Search::InvalidWorkerRequest`. Before binding, any positive request is accepted and checked when capacity becomes known. Binding fails with `InvalidWorkerRequest` if the current request exceeds expanded `Options::threads`. After binding, `request(n > capacity())` throws the same exception. `request()` on an empty handle throws `Search::UninitializedWorkerControl`; empty-handle queries return zero and `operator bool()` is false. Binding and requesting must be serialized inside the shared state so a construction race either accepts a request within capacity or reports the range error, never installs an out-of-range value.
> 
> An absent `Options::worker_control` preserves fixed-at-maximum behavior and the unchanged scheduling path. In a build without thread support, ordinary no-thread engine selection and diagnostics remain unchanged. An engaged control can bind to a sequential engine only with effective capacity one; `request(1)` is a no-op and all other requests are invalid. A request for parallel construction must still receive the existing no-thread diagnostic rather than silently acquiring resize semantics.
> 
> PBS carries controls but allocates no workers by policy. For a multi-asset PBS, controls come from each `SEB` builder's own `Options::worker_control`; PBS preserves those values while replacing only stop and clone settings. The outer PBS options must have an empty control when there is more than one asset, because broadcasting one handle into cloned homogeneous assets would give `capacity()` and one-engine ownership ambiguous meanings. Users needing controllable homogeneous assets construct explicit builders. If parallel PBS drops excess builders because its outer thread count permits fewer assets, those builders' controls remain unbound (`capacity() == 0`). The portfolio controller alone decides requests.
> 
> Expose `requested()` and `capacity()`, but not effective-active count in version one. Effective activity is a transient scheduler property: it can temporarily exceed a new request during cooperative shrink, become zero while `next()` is not exploring, and change between observation and policy action. A public value would therefore be neither a stable allocation nor a completion acknowledgement. Correctness tests should use internal scheduler instrumentation keyed by request generation, including the high-water execution-slot count and convergence acknowledgement. A later API can expose an explicit acknowledgement or generation if portfolio measurements prove it necessary.
> 
> Minimal per-asset portfolio use:
> 
> ```cpp
> Search::WorkerControl left(4);
> Search::WorkerControl right(1);
> 
> Search::Options lo;
> lo.threads = 4;
> lo.worker_control = left;
> Search::Options ro;
> ro.threads = 4;
> ro.worker_control = right;
> 
> SEBs assets { dfs<Model>(lo), dfs<Model>(ro) };
> Search::Options po;
> po.threads = 2; // admit both assets; not an allocation policy
> PBS<Model,DFS> portfolio(root, assets, po);
> 
> Model* solution = nullptr;
> std::thread searching([&] { solution = portfolio.next(); });
> left.request(1);   // safe while next() is running
> right.request(4);
> searching.join();
> ```
> 
> Ownership alternatives were considered. A raw pointer in `Options` is small but can dangle after an `Options` copy or builder delay and is unsafe against destruction. Engine-owned state plus a non-owning observer has the same destruction race and cannot survive RBS child replacement. A shared pointer exposed directly in `Options` is safe but leaks representation and permits null/shared-state misuse at every call site. The selected copyable value hides ref-counting, gives empty state one defined meaning, preserves identity through current meta-engine copies, and permits the implementation to change its synchronization primitive without changing the public API.

## Findings

### Capacity and request have different lifetimes

> `Options::threads` must be expanded once and retained as immutable capacity; the runtime request is a separate integer in `1..capacity`. Worker identities and lifecycle barriers cannot be resized.

Evidence:
- `.zd/parallel-search-worker-control/brief.md` — > - `Search::Options::threads` remains the construction-time maximum and fixes the worker array, worker identities, and reset and termination barrier membership.
> - The runtime limit is an integer in `1..maximum`. Supporting zero active workers is out of scope because a fully parked PBS asset cannot observe portfolio stop requests without another wakeup mechanism.
- `gecode/search.hh` — > /// Number of threads to use
>       double threads;

### The update is a cooperative request, not a synchronous resize

> `request(n)` must return without waiting for workers. Workers observe it at safe exploration boundaries; parked workers retain their search state, and a wakeup makes growth and lifecycle commands visible.

Evidence:
- `.zd/parallel-search-worker-control/brief.md` — > - Parked workers retain their current space, path, statistics, and BAB incumbent state. They may keep an operating-system thread blocked, but they do not consume a search execution slot.
- `.zd/parallel-search-worker-control/brief.md` — > - A limit change is asynchronous and takes effect at safe exploration boundaries. It does not interrupt propagation or recomputation.
- `.zd/parallel-search-worker-control/brief.md` — > - Make the external update operation thread-safe, nonblocking, and usable while another thread is blocked in `next()`.
> - Keep the maximum immutable for the engine lifetime.

### A value handle fits copied Options and builders

> `Builder` stores `Options` by value and exposes that stored copy. A `WorkerControl` member that shares hidden state preserves external identity across the copy without depending on the address or lifetime of either `Options` object.

Evidence:
- `gecode/search.hh` — > class GECODE_SEARCH_EXPORT Builder : public HeapAllocated {
>   protected:
>     /// Stored and already expanded options
>     Options opt;
- `gecode/search.hh` — > /// Initialize with options \a opt and \a best solution search support
>     Builder(const Options& opt, bool best);
>     /// Provide access to options
>     Options& options(void);
>     /// Provide access to options
>     const Options& options(void) const;
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > The approved plan calls for an external asynchronous control handle that survives copied Options, RBS restarts, and per-asset PBS construction without exposing internal slave engines.

### RBS must preserve one logical control across child reset or replacement

> RBS expands and copies its meta options into child options, then repeatedly resets the same child engine. The control should bind to the logical RBS lifetime and be transported to the child rather than rebound as an unrelated engine.

Evidence:
- `gecode/search/rbs.hpp` — > Search::Options e_opt(m_opt.expand());
>     Search::Statistics stat;
>     e_opt.clone = false;
>     e_opt.stop  = Search::Seq::rbsstop(m_opt.stop);
- `gecode/search/rbs.hpp` — > e = Search::Seq::rbsengine(origin,e_opt.stop,
>                                  Search::build<T,E>(variant,e_opt),
>                                  stat,m_opt,E<T>::best);
- `gecode/search/seq/rbs.cpp` — > Space* variant = origin;
>         origin = origin->clone();
>         complete = variant->variant(mi);
>         e->reset(variant);

### PBS already transports per-builder Options and relinquishes builders

> The explicit-builder PBS paths retain each builder's options except for stop and clone, build the asset, and immediately delete the builder. A shared value handle therefore reaches the child and remains alive independently of the deleted builder.

Evidence:
- `gecode/search/pbs.hpp` — > // Re-configure variant options
>       stops[i] = Par::pbsstop(sebs[i]->options().stop);
>       sebs[i]->options().stop  = stops[i];
>       sebs[i]->options().clone = false;
- `gecode/search/pbs.hpp` — > variants[i] = (*sebs[i])(variant);
>       delete sebs[i];
- `gecode/search/pbs.hpp` — > // Delete excess builders
>     for (int i=n_variants; i<sebs.size(); i++)
>       delete sebs[i];

### Outer PBS threads admit assets but do not define each builder's capacity

> In the explicit-builder parallel path, outer `threads` limits how many builders are admitted, while each admitted builder keeps its own already-expanded options. This is the correct seam for independent per-asset controls and also explains why controls belonging to discarded builders remain unbound.

Evidence:
- `gecode/search/pbs.hpp` — > // Limit the number of variants to the number of threads
>     int n_variants = std::min(static_cast<int>(opt.threads),
>                               sebs.size());
- `.zd/parallel-search-worker-control/brief.md` — > - Control individual PBS assets through handles supplied in their search-engine builder options; PBS itself does not implement an allocation policy.

### Homogeneous PBS cannot give one outer handle unambiguous per-asset meaning

> The homogeneous PBS path mutates one copied `Options` and uses it for every asset. A single outer handle would therefore be broadcast into multiple child engines. Multi-asset controlled PBS should require explicit builders instead.

Evidence:
- `gecode/search/pbs.hpp` — > for (unsigned int i=0U; i<n_variants; i++) {
>       opt.stop = stops[i] = Par::pbsstop(stop);
>       Space* variant = (i == n_variants-1) ?
>         origin : origin->clone();
>       (void) variant->variant(static_cast<unsigned int>(i));
>       variants[i] = build<T,E>(variant,opt);
>     }

### Shared state removes the destruction callback race

> Parallel PBS waits for each variant's completion before deleting its owned child engine. A control state held strongly by that child remains valid through the wait/join interval. Putting the wake primitive in the shared state avoids a raw callback into a concurrently destroyed engine.

Evidence:
- `gecode/search/par/pbs.hpp` — > Variant<Collect>::~Variant(void) {
>     delete engine;
>     delete stop;
>   }
- `gecode/search/par/pbs.hpp` — > PBS<Collect>::~PBS(void) {
>     // A report can make n_busy zero before Variant::run and Thread::Run::exec
>     // have returned.  Wait for the completion handshake before deleting the
>     // PBS-owned variants.
>     for (unsigned int i=0U; i<n_variants; i++)
>       variants[i]->wait();
>     assert(n_busy == 0);
>     for (unsigned int i=0U; i<n_variants; i++)
>       delete variants[i];

### Absent controls and non-thread builds need explicit compatibility semantics

> An empty control must preserve current engine selection. The captured PBS constructor chooses parallel execution only under `GECODE_HAS_THREADS` and otherwise uses sequential PBS, so control support must not silently invent parallel behavior in a no-thread build.

Evidence:
- `gecode/search/pbs.hpp` — > #ifdef GECODE_HAS_THREADS
>     if (opt.threads > 1.0)
>       e = Search::pbspar<T,E>(origin,stat,opt);
>     else
> #endif
>       e = Search::pbsseq<T,E>(origin,stat,opt);
- `.zd/parallel-search-worker-control/brief.md` — > - Non-threaded builds retain their current behavior and diagnostics.

### Requested and capacity are stable public observations; effective-active is not

> Expose the immutable bound capacity and atomic requested ceiling. Keep effective-active internal in version one because cooperative convergence and idle periods make an instantaneous public count ambiguous; validate the ceiling with request-generation-aware scheduler instrumentation.

Evidence:
- `.zd/parallel-search-worker-control/brief.md` — > - Should the public type expose only the requested limit, or also observable capacity and effective-active counts for portfolio feedback and tests?
- `.zd/parallel-search-worker-control/brief.md` — > - The observed number of workers executing search never exceeds the requested limit after cooperative convergence.

## Limitations

- The packet does not capture the parallel DFS/BAB worker classes. It supports the public ownership boundary but cannot choose the internal wake primitive or prove that a shared-state event integrates with the worker state machine.
- The minimal example demonstrates the intended API shape; no captured source contains `WorkerControl`, so it cannot compile until implementation.
- One-control/one-logical-engine binding deliberately rejects accidental reuse through copied Options. A reviewed API decision is still needed on whether sequential reuse after destruction is valuable enough to justify generations.

## Recommendations

- Review the names `WorkerControl`, `Options::worker_control`, `requested()`, `request(n)`, and `capacity()` before implementation; keep the public class representation opaque.
- Specify an internal attachment generation owned by RBS so a child replacement can inherit the logical binding without permitting unrelated engines to share it.
- Reject an engaged outer control for multi-asset PBS and direct users to the `SEBs` constructor; test that each admitted builder controls only its own asset and discarded builders remain unbound.
- Add API tests for zero, pre-bind request above capacity, post-bind request above capacity, empty-handle request, second-engine attachment, copied Options identity, request-versus-bind races, and request-versus-destruction races.
- Use internal generation-tagged counters to validate cooperative convergence and execution-slot high-water marks; defer a public effective-active or acknowledgement API until portfolio benchmarks establish a concrete consumer.
- Preserve the empty-control path as the fixed-limit compatibility path and benchmark it separately from the engaged-but-unchanged path.
