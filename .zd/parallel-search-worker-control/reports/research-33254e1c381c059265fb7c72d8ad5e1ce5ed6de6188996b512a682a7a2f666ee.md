# Research report: parallel-search-worker-control

## Question

> Research issue parallel-search-worker-control-002: Specify worker-control API and meta-engine ownership

## Summary

> Yes. The user-approved WorkerControl design satisfies all four acceptance criteria and the requested example deliverable. Expanded `Options::threads` remains immutable capacity; `request()` publishes an asynchronous limit in `1..capacity`. The opaque copyable value shares safe state through Options copies, builders, RBS replacement children, PBS asset construction, and engine destruction. Explicit PBS builders carry independent per-asset controls without giving PBS an allocation policy. Invalid limits, empty controls, one-control/one-logical-engine binding, and non-threaded behavior are explicit. Version one exposes requested and capacity but deliberately defers effective-active observability. The retained example demonstrates external portfolio reallocation while `next()` runs. This completes the reviewed API specification, not its later implementation.

## Findings

### Capacity and asynchronous request semantics are explicit

> Expanded threads is immutable capacity. Positive requests bind within that capacity, and zero or above-capacity requests are errors.

Evidence:
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > `Options::threads`, after expansion, remains the immutable construction-time
> capacity. An engaged handle owns hidden reference-counted state shared by the
> caller, copied Options, builders, meta-engines, and the attached logical
> engine. The state contains the atomic requested limit and wakeup generation;
> `request()` never dereferences an engine.
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > `WorkerControl(n)` creates unbound state with an initial positive request.
> Binding publishes the expanded immutable capacity and rejects a request above
> it. `request(0)`, construction with zero, and post-bind requests above capacity
> are errors.

### Shared ownership prevents dangling controls

> The value handle preserves identity through copied Options and builders, RBS carries an attachment generation across child replacement, and destruction detaches only after workers join.

Evidence:
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > One public control identity binds to one logical engine. Constructing a second
> unrelated engine from copied Options containing the same bound control is an
> error. RBS owns the logical binding and transports an internal attachment
> generation to replacement child engines, so restart does not create a second
> binding.
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > Engine destruction retains the shared state until parked workers have
> been woken and joined, then detaches it. External copies remain memory-safe;
> later requests update inert state and cannot call a destroyed engine.

### PBS transports independent controls without policy

> Explicit asset builders provide distinct controls. Ambiguous homogeneous broadcast is rejected, and PBS never chooses requests.

Evidence:
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > PBS transports controls but implements no allocation policy. Explicit
> multi-asset PBS obtains one control from each asset builder's Options. Controls
> for builders discarded by outer PBS admission remain unbound.
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > A single engaged
> outer control is rejected for homogeneous multi-asset PBS because broadcasting
> one identity into several logical engines would make ownership and capacity
> ambiguous; users who need controlled homogeneous assets construct explicit
> builders.

### Compatibility, errors, and observability are bounded

> Empty controls retain current behavior; sequential no-thread binding supports capacity one only. Public observations are requested and capacity, with effective-active deferred.

Evidence:
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > An empty `Options::worker_control` preserves current fixed-at-maximum behavior.
> In a build without thread support, ordinary engine selection and diagnostics
> remain unchanged. A sequential engine may bind only at capacity one;
> `request(1)` is a no-op and other limits are invalid.
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > Version one exposes `requested()` and `capacity()`, but not an
> effective-active count. Effective activity is transient during cooperative
> shrink, can be zero while `next()` is not exploring, and changes between
> observation and policy action.

### The required portfolio example is recorded

> The example constructs two independently controlled assets and changes their requests while portfolio search is running.

Evidence:
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > SEBs assets { dfs<Model>(lo), dfs<Model>(ro) };
> Search::Options po;
> po.threads = 2; // Admit both assets; this is not an allocation policy.
> PBS<Model,DFS> portfolio(root, assets, po);
> 
> Model* solution = nullptr;
> std::thread searching([&] { solution = portfolio.next(); });
> left.request(1);
> right.request(4);
> searching.join();
- `.zd/parallel-search-worker-control/issues/002-specify-worker-control-api-and-meta-engine-ownership.md` — > The user approved this design on 2026-07-24.

## Limitations

- This result proves the reviewed public API and ownership specification, not the later implementation or executable example build.
- Exact exception class spellings and private representation remain implementation details.
